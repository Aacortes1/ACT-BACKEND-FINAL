## Decisión de permisos

- Rutas autenticadas: todas las rutas bajo `/api/tasks` y `GET /api/auth/me`.
- Ruta exclusiva de admin: `DELETE /api/tasks/:id`.
- Justificación: la autenticación confirma la identidad del JWT y la autorización separa el permiso de borrado; el rol se administra desde terminal, sin una ruta pública para autoasignarse admin.
- Alcance: la guía aplica permisos por rol. Las tareas aún no tienen propietario y no se afirma que cada usuario vea solo sus tareas.

## Preguntas de cierre

1. Un token que se puede decodificar aún puede tener firma inválida, estar expirado o declarar un issuer/audience incorrecto. `verifyAccessToken` valida esas condiciones.
2. Se usa 401 cuando falta una credencial válida y 403 cuando el usuario sí está autenticado, pero su rol no tiene permiso.
3. CORS controla qué respuestas puede leer el JavaScript de un navegador; clientes como Postman o curl no dependen de esa política y CORS no identifica usuarios.
4. Si `DELETE` se registra antes de `requireRole`, la solicitud podría llegar al controlador de borrado sin pasar por la autorización.
5. El rol forma parte del JWT emitido al iniciar sesión; después de cambiarlo en MongoDB hay que volver a iniciar sesión para obtener un token con el nuevo claim.
6. Express 5 reenvía automáticamente los rechazos de una promesa de middleware al manejador central de errores.
7. El almacén en memoria del limitador no comparte contadores entre instancias y se reinicia al reiniciar el proceso.
8. Autorizar por propietario requeriría agregar `userId` a tareas, migrar documentos existentes y filtrar las operaciones del repositorio por usuario, además de definir qué puede hacer admin.
